# 프로젝트 팁

### 프로젝트 진행 방식

이번 프로젝트 역시 3주간의 짧은 시간동안 단기 스프린트로 진행해야 하는 애자일 방식을 따릅니다. 따라서  빠른 이터레이션(반복)을 위해 타임박싱(Time-boxing)을 엄격하게 해야 할 필요가 있습니다.

**스프린트의 기간과 몇 번의 반복이 수행될지에 대한 일정 수립**

- 주단위 스플린트의 경우 3주간 3번의 반복만 수행
- 일단위 스플린트를 통해 일차에 따른 스플린트 일정을 미세하게 조정하여 더욱 많은 반복을 수행(추천)

**각 스플린트에서 수행할 목적과 리스크를 작성하고 스프린트가 끝날 때 마다 회고 진행**

- 매일 10~15분씩 데일리 스크럼(Daily Scrum)을 추가 진행하여 ****`[어제 한 일 / 오늘 할 일 / 막히는 부분(Blocker)]`을 공유하여 투명성을 유지
- 스프린트 회고에서는 KPT(Keep, Problem, Try)를 진행
    - Keep: 좋았던 점, 계속 유지할 점
    - Problem: 아쉬웠던 점, 기술적/소통적 문제점
    - Try: 문제를 해결하기 위해 다음 스프린트에 시도할 구체적 액션

### 리더(PM)의  역할

초급 프로젝트에서 리더(PM)의 역할이 많이 중요하다고 느끼셨을 겁니다. 이번에도 역시 PM의 역할이 매우 중요 합니다. 따라서 PM은 팀원과의 원할 한 소통을 통해 다음 가이드 내용을 조율하고 협업을 만들어 갑니다.

**일정 및 스프린트 관리 (Timeline & Sprint)**

- 타임박싱 일정에 맞춰 개발 스코프를 냉정하게 제한합니다. 구현하고 싶은 기능이 많더라도 3주 안에 끝낼 수 없다면 과감히 백로그(보류 과제)로 돌립니다.
- 매일 팀원들의 개발 상황을 체크하고, 특정 파트에서 막힘이 생기면 리소스를 재배치하거나 일정을 즉시 조율하여 병목 현상을 해결합니다.
- 스프린트가 끝날 때마다 간단하게 KPT(Keep, Problem, Try) 회고를 진행하여 다음 스프린트를 원할하게 합니다.

**소통 및 애자일 협업 프로세스 (Communication)**

- 매일 데일리 스크럼을 통해 각 팀원간 수행하는 내용에 대하여 투명성을 유지해 줍니다. 데일리 스크럼이 아니더라도 필요하면 그때 그때 바로 소통을 통해 주요 이슈들을 공유합니다.
- 일일 통합(Daily Merge) 원칙을 세워 각자 개발한 내용을 마지막에만 합치기 보단 최소 2일 단위로 코드를 GitHub에 머지하고 통합 테스트를 수행하도록 리드합니다.
- 프롬프트 실험 결과, Chunking 전략, API 명세서 등이 파편화되지 않도록 노션이나 GitHub Issue에 기록하는 규칙을 만듭니다.

**베이스라인 설계 및 기술 조율 (Baseline & Tech Stack)**

- 이번 실습에는 PDF, Markdown, Doc 등의 문서 데이터가 주로 활용되므로 데이터를 어떻게 공유하고 추가 수집할지 기본적인 데이터 파이프라인 정리가 필요합니다.
- 이번 실습에는 GCP의 인스턴스를 추가로 활용하므로 기본적인 VM 세팅과 공유 환경을 세팅해야 합니다.
- 챗봇에 추가될 수 있는 기능(에이전트화)들을 제공하고자 하는 서비스에 맞게 설계하고 이에 따른 역할을 배정합니다.
- 기본적인 서비스 형태에 대한 디자인 설계, 서빙 방식, 네트워크 구조 등 큰 그림을 설계합니다.
- 챗봇의 충실도(Faithfulness), 답변 관련성(Answer Relevance) 등을 정량 지표화하기 위한 골든 데이터셋(질문-정답 쌍 50~100개)을 조기에 구축해 놓습니다.
- 모델의 어떤 평가적 기준을 둘지를 우선순위에 따라 목록을 정리하고, 이에 맞는 모델 후보를 찾고 실험을 통해 최종 모델을 찾습니다.

### 추가 할만한 에이전트 도구 기능 예시

다음은 이번 주제인 B2G 입찰지원 전문 컨설팅 서비스에 필요할 만한 에이전트 도구 예시입니다. 요구되는 데이터를 확보 할 수 있는지, API 가 존재하는지 등 확인하여 다양한 부가 기능을 제공하여 더욱 완성도 높은 에이전트로 확장해 봅니다.

- **기업 신용도 및 실적 매칭 API (Firmographic Matcher)**
    - **기능:** 나라장터 등에서 요구하는 신용평가등급(e.g., BB- 이상), 기업 규모(중소기업자간 경쟁제품 여부), 최근 3~5년간의 유사 사업 수행 실적(실적 금액 누계) 항목을 기업 내부 DB(ERP)와 비교하여 입찰 가능 여부를 1차 판정합니다.
- **신인도 가감점 계산기 (Score Calculator)**
    - **기능:** B2G 입찰의 당락을 가르는 신인도 평가 점수(가점: 고용창출, 신기술 인증, 여성/장애인기업 등 / 감점: 부정당업자 제재 이력, 임금체불 등)를 정량적으로 계산해 주는 도구입니다.
- **발주처 과거 낙찰 트렌드 분석기 (Buyer Profiler)**
    - **기능:** 조달청 개찰 결과 데이터를 기반으로 해당 발주처가 과거에 유사 사업에서 투찰 금액(가격점수)을 중요하게 보았는지, 혹은 기술 점수로 당락이 갈렸는지를 시각화하고, 주로 낙찰받았던 상위 3개 업체의 특징을 요약합니다.
- **경쟁사 제안 패턴 분석기 (Competitor Tracker)**
    - **기능:** 웹 검색 도구로 경쟁 후보사들의 과거 수주 이력, 언론 보도, 특허 및 보유 기술 정보를 크롤링·분석하고, 경쟁사가 들고나올 가능성이 높은 핵심 아키텍처나 전략을 예측하고 이에 대응할 논리를 추천합니다.
- **RFP-목차 매칭 및 템플릿 제너레이터 (Structure Mapper)**
    - **기능:** RFP 파일에서 제안서 작성 지침과 평가 항목을 추출하여, 규격에 맞는 제안서 기본 목차(WBS 구조 포함)와 한글(HWP)/Word 템플릿을 자동으로 생성합니다.
- **조달 가격(투찰가) 시뮬레이터 (Pricing Simulator)**
    - **기능:** 예가 산출 방식(복수예비가격 등)을 고려하여, 기술 점수 예측치에 따른 최적의 합격권 투찰 금액 구간을 시뮬레이션하고 제안서 내 가격 제안 부분의 논리를 뒷받침할 데이터를 생성합니다.
- **제안요청서 대비 누락 체크 도구 (Compliance Matrix Validator)**
    - **기능:** RFP에서 요구한 필수 제출 서류 및 기술 요구사항(e.g., "반드시 ~를 포함할 것") 리스트와 작성 중인 제안서 초안을 비교하여, 누락된 요구사항이나 미기재된 페이지를 찾아내는 Cross-Check 도구입니다.
- **국가계약법 및 계약예규 적합성 검증기 (Legal Checker)**
    - **기능:** 제안서 내에 포함된 문구나 조건이 최신 국가계약법, 지방계약법, 혹은 소프트웨어 진흥법(e.g., 과업변경 시 대가 지급, 원격지 개발 규정 등)에 위배되거나 독소 조항이 될 소지가 없는지 검토합니다.
- **제안서 레이아웃 및 시각화 가시성 평가기 (Layout & UX Auditor)**
    - **기능:** 완성된 제안서 페이지(PDF/이미지)의 가독성을 평가합니다. 텍스트가 너무 빽빽한 구간, 화살표 흐름이 어색한 아키텍처 다이어그램, 폰트 크기 불균형 등을 찾아내고, "이 부분은 3단 도식화로 변경하는 것이 직관적입니다" 같은 시각적 개선 피드백을 줍니다.
- **증빙 서류 자동 검증기 (Compliance Document OCR)**
    - **기능:** 제출한 사업자등록증, 신용평가서, 특허증, 기술인력 자격증(PDF/이미지)을 Vision 모델로 스캔합니다. 서류의 내용을 제안서에 자동 입력해주거나, 만료 기한, 주소지 불일치, 도장 누락 등 단순 서류 미비로 인한 탈락 리스크를 원천 차단합니다.
- **발표 평가(PT) 스크립트 감성 및 전달력 코칭**
    - **기능:** 제안서 제출 후 진행되는 PT 발표 스크립트를 분석 합니다. 문장의 어조가 너무 방어적인지, 혹은 지나치게 공격적인지 판단하여 심사위원(공무원/교수)들이 선호하는 신뢰감 있고 객관적인 어조(Confidence & 서술형 톤)로 변경하고 키워드 강조의 배치를 적절하게 교정해줍니다.

### 컴퓨팅 자원 활용 팁

이번 프로젝트에는 GCP VM 서버가 제공되므로 코랩 외에 활용할 수 있는 컴퓨팅 자원이 확보가 됩니다. 해당 VM을 활용하는 방식은 다음 팁을 참고하여 팀별로 자유롭게 활용해 주시면 되겠습니다. 참고로 서빙에 대한 개념은 파트 4에서 배우기 때문에 이번에는 간단하게 개발 용도나 Ollama 서빙 용도 정도로 활용을 추천합니다.

- **VM 사양**
    - 제공 되는 VM은 메모리 16GB에 L4 GPU가 지원되어 코랩 과 유사한 컴퓨팅 자원을 가지고 있습니다. 이는 경량화 된 LLM 모델(~ 8B 정도)을 미세조정 하거나 추론하는데 활용할만한 수준입니다.
    - 디스크 크기가 100GB로 제한되고 메모리도 큰편이 아니라서 너무 큰 LLM 모델을 활용하면 캐시 부족이나 병목 현상이 생길 수 있습니다.
    - 권장 이미지(ubuntu-accelerator-2204-amd64-with-nvidia-550)는 리눅스 운영체제를 사용하기 때문에 리눅스 명령어 체계에 대한 간단한 이해가 필요합니다.
    
    [리눅스 명령어 참고](https://namu.wiki/w/Unix/%EB%AA%85%EB%A0%B9%EC%96%B4)
    
- **개발 과정에서 활용하기**
    - VM을 하나의 코랩처럼 활용해 개발 과정에서 컴퓨팅 자원으로 활용할 수 있습니다. 다만 이번 프로젝트 특성상 여러 명이 동시에 활용하기에는 자원이 부족하므로, 기본적으로 코랩을 쓰고 부족한 자원에 대해 부가적으로 활용하는 것이 좋아 보입니다.
    - VM을 코랩 처럼 운용하기 위해 가이드에 안내되어있는 주피러 랩을 설치하고 포트포워딩 하여 코랩처럼 활용해 주시면 됩니다.
- **최종 배포의 목적으로 활용하기(서버)**
    - VM 성능이 경량화된 LLM 모델을 구동하기에는 충분합니다. 따라서 LLM 모델을 Fast API등으로 감싸 OpenAI의 Chat Completion 방식으로 통신 API를 구축하거나 Ollama 서버로 모델을 구동하여 랭체인 애플리케이션과 연동할 수 있습니다. [Ollama 서버 랭체인 연동하기](https://app.notion.com/p/Ollama-6462af9189a583be8dab81785e992fb4?pvs=21)
    - 랭체인 자체를 VM 서버에 구축해놓고 Fast API로 감싸 프론트에서 백엔드로 접근할 수 있게 서버를 구축 할 수 있습니다. 이 경우에는 사용하는 도구가 무겁고 LLM이 크다면 메모리나 디스크가 부족해 불가능 할 수 있고, Fast API와 도커 설정등이 따르므로 파트 4 내용이 필요합니다.
    - VM을 MCP 서버로 구현할 수 있습니다. 도구를 직접 랭체인에서 tool 데코레이팅 함수로 구현하지 않고 VM에 따로 구현하여 Fast API 등으로 감싸 랭체인에서 통신으로 호출 하는 방식입니다. Fast API와 도커 설정등이 따르므로, 파트 4를 배우고 도전해 봅시다.
    - VM을 서버로 활용하는 경우 굳이 주피터 랩을 설치할필요 없습니다. GCP의 SSH 셀 기능을 이용하거나 VS code, 파이참을 이용하여 SSH 연동 후에 활용하는 것을 추천합니다.
