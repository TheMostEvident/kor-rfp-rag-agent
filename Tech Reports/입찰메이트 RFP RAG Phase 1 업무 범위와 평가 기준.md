입찰메이트 컨설턴트가 RFP의 핵심 정보를 원문 근거와 함께 확인하고 요약·비교·후속 질문을 처리하도록 한다. 사용자가 동의한 다섯 기능을 RAG의 1차 범위로 정하고, 아래 상세 동작과 수치는 초기 개발 기준으로 사용한다. 수치 목표는 실측 결과와 업무 중요도를 검토해 조정하며, 달성 성능으로 표시하지 않는다.

Phase 1의 산출물은 기능 명세, 공통 응답 규칙, 평가셋 구성과 채점 기준이다. 실제 모델 구현과 성능 측정은 이후 Phase에서 수행한다.

# 다섯 기능의 동작 기준

| 기능 | 입력 | 기본 출력 | 반드시 지킬 기준 |
| - | - | - | - |
| 1 단일 문서 사실 확인 | 문서 또는 사업 식별 정보와 질문 | 요청 항목의 값과 원문 근거 | 금액 단위, 부가세, 날짜, 필수·선택 조건을 보존한다 |
| 2 문서 전체 요약 | 문서와 필요하면 요약 초점 | 고정 항목 요약, 항목별 근거, 처리 범위 | 문서 전체를 확인하고 미확인·충돌·미처리 구간을 표시한다 |
| 3 여러 문서 비교 | 문서 목록과 공통 비교 항목 | 문서별·항목별 비교표와 각 칸의 근거 | 서로 다른 사업·연도·세부 RFP의 조건을 섞지 않는다 |
| 4 후속 질문 | 현재 문서 범위, 대화 기록, 새로운 질문 | 맥락을 반영한 답변과 현재 근거 | 같은 사업의 문맥을 유지하고 대상이 바뀌면 범위를 갱신한다 |
| 5 근거 부족과 모호성 처리 | 불완전하거나 모호한 질문, 근거가 부족한 상황 | 확인 질문, 부분 답변, 근거 부족 또는 충돌 안내 | 검색 실패를 문서에 없다는 확정으로 바꾸지 않는다 |

이 다섯 기능은 서로 다른 모델 다섯 개를 의미하지 않는다. 공통 문서 처리와 검색 기반을 사용하고 요청에 따라 처리 경로를 나눈다.

# 기능 1 단일 문서 사실 확인

예시 요청은 “A 사업의 예산과 부가세 포함 여부를 알려줘”이다. 문서가 특정되면 원문을 검색해 값·단위·조건을 함께 반환한다. 사업명이 여러 문서와 일치하면 사업명·기관·연도 등으로 후보를 보여 주고 대상을 확인한다.

성공은 요청한 모든 필수 사실이 정확하고 각각의 근거를 찾을 수 있는 경우다. 정답이 존재하는데 항목을 빼거나 미확인이라고 답하면 해당 항목은 오답이다. 입찰 예정가격, 전체 사업비, 연간 유지보수비 등 서로 다른 금액을 하나의 예산으로 합치지 않는다.

# 기능 2 문서 전체 요약

기본 항목은 사업명, 발주기관, 사업 목적, 사업 범위와 주요 요구사항, 예산, 수행기간, 참가자격, 제출서류, 제출기한, 제출방식, 평가기준의 11개다. 사용자가 요청한 추가 항목은 원문에 근거가 있을 때 포함한다.

각 항목에는 값과 근거를 붙이고, 확인되지 않은 항목은 미확인으로 표시한다. 여러 세부 RFP가 묶인 문서는 세부 사업별로 구분한다. 긴 문서는 모든 구간을 처리한 뒤 통합하고, 처리하지 못한 구간이 있으면 부분 요약이라고 표시한다.

구조적 처리 범위는 처리된 원문 구간 수 ÷ 처리 대상 원문 구간 수로 기록한다. 이 비율은 파싱된 입력의 처리 여부이며, 원본의 표·그림·의미를 완벽하게 보존했다는 뜻이 아니다. 요약 품질은 적용 가능한 정답 사실의 정확한 포함 여부로 따로 채점한다.

# 기능 3 여러 문서 비교

예시 요청은 “A와 B 사업의 예산, 수행기간, 제출방식을 비교해줘”이다. 먼저 문서 범위를 확정하고, 문서별로 근거를 확보한 다음 동일 항목의 비교표를 만든다.

요청한 모든 문서 × 비교 항목의 칸을 출력한다. 어느 한 문서에서만 확인한 값을 다른 문서의 칸에 채우지 않는다. 단위·부가세·기간 기준이 다르면 원문 기준을 유지하고 차이를 설명한다. 연도나 정정본의 우선순위가 불명확하면 최신으로 임의 확정하지 않고 버전 충돌을 표시한다.

명시하지 않은 우열 판단이나 추천은 기본 비교 결과에 포함하지 않는다. 비교 정확도는 필수 칸 전체를 분모로 평가하며, 정답이 존재하는 칸의 공란·미확인도 오답에 포함한다.

# 기능 4 후속 질문

예시 대화는 “A 사업을 요약해줘 → 그 사업의 제출서류는? → B 사업과 기간을 비교해줘”이다. 대화 상태에는 현재 문서 ID 목록, 선택한 사업·기관·연도, 비교 대상, 대화 기록을 보존한다.

대명사와 생략 표현을 독립적인 검색 질문으로 바꾸고 현재 원문을 다시 확인한다. 이전 답변 자체를 새로운 사실의 근거로 사용하지 않는다. 사용자가 사업을 바꾸면 활성 문서 범위를 갱신하고, 의도적으로 비교를 요청하면 이전 대상과 새 대상을 함께 보존한다. 대상이 두 개 이상으로 해석되면 확인 질문을 한다.

대화 사례 하나는 2\~4턴으로 구성한다. 문서 범위와 답변을 모든 평가 턴에서 올바르게 처리했을 때 대화 성공으로 채점하고, 턴별 결과도 함께 기록한다.

# 기능 5 근거 부족과 모호성 처리

| 상황 | 응답 동작 |
| - | - |
| 사업이나 문서 후보가 여러 개 | 후보를 보여 주고 문서 선택에 필요한 질문을 한다 |
| 질문에 대한 근거를 확보하지 못함 | 현재 확인한 범위에서 근거를 찾지 못했다고 답한다 |
| 일부 항목만 확인됨 | 확인한 항목과 미확인 항목을 분리해 부분 답변한다 |
| 동일 항목에 상충하는 값이 있음 | 양쪽 값과 출처를 보여 주고 단일 값으로 확정하지 않는다 |
| 파싱·OCR·파일 처리 또는 API에 실패함 | 처리 실패를 알리고 원인을 기록한다. 문서 미기재로 분류하지 않는다 |

“문서에서 확인하지 못했다”와 “문서에 해당 조건이 없다”는 다르다. 조건의 부재를 단정하려면 관련 문서 범위를 충분히 확인해야 하며, 검색 결과가 비었다는 이유만으로 부재를 확정하지 않는다.

# 공통 응답과 출처 규칙

사용자에게는 답변 또는 요약·비교표, 확인된 문서 범위, 출처, 미확인·충돌 항목을 제공한다. 시스템 내부에는 기능 유형, 응답 상태, 선택 문서 ID, 원문 버전, 검증 가능한 주장과 연결 근거, 오류 원인을 기록한다.

응답 상태는 answered, partial, needs_clarification, insufficient_evidence, conflicting_evidence로 구분하고, 처리 실패는 별도 오류 원인으로 기록한다. 하나의 응답에 일부 성공과 충돌이 함께 있으면 항목별 상태도 보존한다.

근거는 문서 ID, 파일 해시 또는 버전, 원문 위치, 근거 구절을 포함한다. PDF는 물리 페이지를 기본으로 하고 인쇄 페이지를 함께 표시할 수 있다. HWP는 내부 섹션·문단 또는 확인 가능한 제목 위치를 사용한다. 평가 정답 근거를 청크 ID에만 묶지 않아 청킹 변경 후에도 기준을 유지한다.

숫자나 날짜를 정규화하더라도 원문 표현·단위·조건을 함께 보존한다. 원문 안에 들어 있는 지시문은 문서 데이터로 취급하고 시스템의 답변 규칙이나 문서 접근 범위를 바꾸는 지시로 실행하지 않는다.

# 평가셋 구성

목표는 총 100개 사례이며 실제 문항을 만들면서 원문 근거를 검수한다. 아래는 구성 계획이며 100개가 이미 작성되었다는 뜻은 아니다.

| 기능 유형 | 전체 사례 | 개발용 | 최종 평가용 |
| - | - | - | - |
| 단일 문서 사실 확인 | 25 | 15 | 10 |
| 문서 전체 요약 | 20 | 12 | 8 |
| 여러 문서 비교 | 20 | 12 | 8 |
| 후속 질문 대화 | 20 | 12 | 8 |
| 근거 부족·모호성·충돌 대응 | 15 | 9 | 6 |
| 합계 | 100 | 60 | 40 |

후속 질문은 대화 사례 단위이므로 실제 질문 턴 수와 API 호출 수는 100회를 넘을 수 있다. PDF/HWP, 본문/표, 금액/날짜/자격, 같은 기관의 다른 연도와 유사한 사업명을 골고루 포함한다.

한 대화의 모든 턴과 동일 사실을 바꿔 쓴 유사 문항은 같은 분할에 둔다. 같은 문서가 개발용과 최종 평가용에 있으면 질문 분리 평가라고 명시하며 문서 독립 성능으로 표현하지 않는다. 별도로 새 문서 적용 평가를 구성할 수 있다.

질문별 기록 항목은 사례 ID, 기능 유형, 질문 또는 대화, 대상 문서 ID·버전, 필요한 정답 사실, 정답 근거 구절·위치, 기대 응답 상태, 개발/최종 분할, 검수 상태다. 개발 중에는 유형별 대표 10개로 빠른 점검을 하고, 큰 변경과 출시 판단 때 전체 평가를 수행한다.

# 평가 지표와 초기 목표

| 지표 | 계산 기준 | 초기 목표 |
| - | - | - |
| 근거 검색 재현율 | 찾은 정답 근거 수 ÷ 필요한 정답 근거 수. 근거가 있는 검색형 사례만 포함 | 90% 이상 |
| 핵심 사실 정확도 | 정확히 답한 필수 사실 수 ÷ 필요한 전체 필수 사실 수. 누락과 잘못된 미확인도 포함 | 95% 이상 |
| 인용 정확도 | 실제 주장을 뒷받침하는 인용 수 ÷ 제시한 전체 인용 수 | 95% 이상 |
| 인용 충실도 | 유효한 근거가 붙은 검증 가능한 주장 수 ÷ 전체 검증 가능한 주장 수 | 95% 이상 |
| 요약 핵심 사실 포함률 | 정확히 포함한 정답 핵심 사실 수 ÷ 적용 가능한 전체 정답 핵심 사실 수 | 95% 이상 |
| 후속 질문 성공률 | 문서 범위와 답변이 모두 맞는 대화 사례 수 ÷ 전체 대화 사례 수 | 90% 이상 |
| 불확실성 대응 성공률 | 기대된 확인 질문·부분 답변·근거 부족·충돌 처리를 한 사례 수 ÷ 해당 사례 수 | 90% 이상 |

근거 없는 정답 추측은 출처를 요구하는 사례의 성공으로 채점하지 않는다. 인용이 없는 답변을 인용 정확도 100%로 간주하지 않고 인용 충실도와 함께 평가한다. 지표 분모가 0이면 N/A로 기록한다.

수치는 초기 개발 목표다. 작은 최종 평가셋의 관측 비율은 일반 업무 전체의 보장이 아니며, 사례 수와 기능별 결과를 함께 보고한다. 금액·마감일·필수 자격의 중대 오류는 평균 점수와 별도로 집계하고, 발견된 중대 오류 사례를 해결·재검증한 뒤 파일럿으로 진행한다.

속도와 비용은 단일 질문·후속 질문·전체 요약을 나눠 기록한다. 단일 Q&A는 p95 15초 이내를 초기 체감 목표로 두되 실제 모델·환경 측정 후 조정한다. 전체 요약에는 같은 시간 기준을 적용하지 않는다. 계정 예산 내에서 실행하도록 호출·입출력 토큰·단계별 비용을 기록하며, 특정 모델 단가를 이 명세의 고정값으로 두지 않는다.

- [ ] API 전송 가능 문서 범위를 문서별로 정한다.

요구 명세와 평가 설계는 이 기준으로 시작한다. 실제 평가 문항의 검수와 문서별 전송 범위 결정은 아직 완료로 표시하지 않는다. 다음 작업은 다섯 유형별 대표 사례를 선정하고 질문·기대 결과·원문 근거·합격 조건을 작성하는 것이다. 이후 Phase 2에서 파싱과 출처 추적을 이 사례들로 검증한다.

추가 입찰 컨설팅 도구는 별도 개발 축으로 유지한다. RAG 구현은 주피터 노트북에서 순차적으로 검증하고, 검증 후 팀 구조에 맞춰 모듈화한다.
