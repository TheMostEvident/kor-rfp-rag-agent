# 입찰메이트 RFP RAG — Phase 5

Phase 4에서 성공한 근거 기반 Q&A·비교를 이어받아 **11개 항목의 전체 문서 요약과 조건 보존 검토**를 추가했습니다. GitHub나 Google Drive를 수정하지 않는 로컬 실행용 패키지입니다.

## 이번 단계의 범위

- 사업명, 발주기관, 목적, 주요 범위·필수요건, 예산·VAT, 수행기간, 참가·수행자격, 입찰 제출서류, 제출기한, 제출방식, 평가기준의 11개 항목을 분리합니다.
- 전체 문서의 청크를 원문 순서대로 배치에 넣고 출처 검증을 통과한 주장만 합칩니다.
- 공고문 참조·미확인·충돌 후보를 구별하고 서로 다른 후보를 남깁니다.
- 숫자·단위·VAT·기간·조건 표현 차이를 진단합니다. 이 진단은 의미적 정답 판정이 아닙니다.
- 실행 결과와 그 결과에 연결된 사람 검토 양식을 저장합니다.

Phase 4의 공백 차이 인용 복원과 두 구간 인용 분리 수정(v2)을 포함했습니다. 별도의 06·07 패치 노트북을 다시 적용할 필요가 없습니다. Phase 3의 데이터·청크·인덱스와 기준 보고서는 보존했습니다.

후속 대화 고도화, 정식 품질·속도·비용 평가, 운영 UI와 RAG 외 추가 업무 도구는 이후 단계입니다. 이번 결과만으로 프로젝트 전체가 완성된 것은 아닙니다.

## 1. 가장 먼저 할 일

1. ZIP을 새 폴더로 압축 해제합니다. 기존 Phase 3·4 폴더에 덮어쓰지 않습니다.
2. VS Code에서 새 `rfp_phase5_local_20261111` 폴더를 엽니다.
3. `notebooks/08_younggwan_phase5_grounded_summary.ipynb`를 엽니다.
4. 노트북 오른쪽 위 커널에서 **기존에 성공한 Phase 3 `.venv/bin/python`**을 선택합니다.
5. 모든 옵션이 `False`인 기본 상태로 **Run All** 합니다.

기존 Python 경로는 다음과 같은 형태입니다.

```text
.../rfp_phase3_local_20261111/.venv/bin/python
```

가상환경 폴더와 이번 프로젝트 폴더가 달라도 됩니다. 이미 동작한 환경이라면 새 가상환경을 다시 만들 필요가 없습니다. 터미널의 가상환경 활성화와 노트북 커널 선택은 별개입니다.

기본 Run All은 99개 고유 문서·18,266개 청크를 검사하고 11개 항목의 전체 요약 계획을 만듭니다. **OpenAI 호출·모의 응답 생성은 모두 0회**입니다. 실제 생성 상태는 `미실행`으로 표시됩니다.

../rfp_phase3_local_20261111/.venv/bin/python -m pip install -r requirements-phase5.txt

의존성은 저장된 인덱스의 버전에 맞춥니다.

## 3. 첫 실제 실행은 전체 요약만

Phase 4의 예산 Q&A·문서 비교는 이미 성공했으므로 이번에는 전체 요약부터 확인하는 편이 좋습니다. 노트북 첫 코드 셀을 다음처럼 바꿉니다.

```python
ENABLE_OPENAI = True
RUN_LIVE_QA = False
RUN_LIVE_SUMMARY = True
```

커널을 Restart한 뒤 Run All 합니다. 로컬 비밀번호 입력창이 나타나면 API 키를 입력합니다. 키를 노트북 셀에 적거나 대화로 보내지 마세요. 출력에는 키 자체 대신 설정 여부만 나옵니다.

기본 요약 문서는 dev 사례 S002인 **인천공항시설관리(주)의 연말정산 위탁운영 용역**입니다. 18개 청크 전체를 기본 설정에서 1개 배치로 요약하며, 실행 전 `map_calls`와 입력 byte 계획을 표시합니다. 현재 기본 계획은 31,301 byte이며, 설정이나 프롬프트를 바꾸면 달라집니다. 전체 요약은 Q&A 한 번보다 여러 API 호출이 필요할 수 있습니다. `can_execute`는 배치 구조의 허용 여부입니다. 별도로 `fresh_session_uncached_within_caps`와 호출·총 입력 상한을 확인하세요. 실제 실행에서는 캐시와 세션의 남은 상한을 모든 배치에 대해 사전 검사하고, 상한을 넘으면 입력을 자르지 않고 차단합니다.

`configs/phase5.json`의 생성 모델·호출 수·입력·출력 상한을 조정할 수 있습니다. 설정 변경 뒤 커널을 Restart하세요. 기본 모델은 `gpt-5.4-mini`입니다. 11개 항목과 원문 인용을 담도록 요청당 출력 상한은 6,000토큰으로 두었습니다. 이는 실제 생성량이 아니라 최대 허용량입니다. 요약 계획의 byte는 토큰 수나 달러 금액이 아닙니다. 실제 사용량이 보고되면 설정된 단가로 추정 비용을 기록하며, 실제 청구서는 별도로 확인해야 합니다.

Phase 5는 요약 항목과 프롬프트가 달라 새 요청이 발생합니다. 기존 Phase 4의 성공 결과를 이번 요약의 API 사용량이나 품질 측정으로 대신 집계하지 않습니다.

## 4. 직접 질문하기

노트북의 문서 선택 셀에서 다음 값을 바꾸고 `RUN_LIVE_QA=True`로 실행합니다.

```python
QA_SELECTED_DOC_IDS = examples['F001']['selected_doc_ids']
QA_QUESTION = '2027년 글로벌 패션브랜드 육성 용역의 용역비는 얼마이며 부가세가 포함되나요?'
QA_FEATURE = 'qa'
```

다른 공개 문서는 출력된 ID 목록에서 선택할 수 있습니다. 비교는 `QA_FEATURE='comparison'`으로 바꾸고 두 문서를 선택합니다. 승인 목록 밖의 문서를 API로 전송하지 않습니다.

선택한 공개 RFP 5개만 기본 승인 목록에 포함합니다. 다른 문서를 추가할 때는 해당 문서의 API 전송 가능 여부를 확인하세요. 승인 목록은 이번 실행의 전송 대상을 제한하는 설정입니다.

## 5. 결과를 읽는 방법

| 상태 | 해석 |
| --- | --- |
| `evidence_found` | 처리한 입력에서 인용 가능한 내용을 찾음 |
| `notice_reference` | 원문이 공고문 확인을 명시함 |
| `conflict_candidates` | 서로 다른 후보를 보존하며 검토가 필요함 |
| `not_found_in_processed_input` | 처리한 입력에서 해당 항목 근거를 확보하지 못함 |
| `not_processed` | 실행되지 않았거나 처리가 끝나지 않음 |

`input_chunk_coverage=1.0`은 모든 청크가 응답을 받은 입력에 들어갔다는 뜻입니다. `validated_chunk_coverage=1.0`은 해당 입력의 출처 검사를 통과했다는 뜻입니다. 둘 모두 요약의 의미적 완전성이나 정답률을 뜻하지 않습니다.

공고문 참조는 **원문에 실제로 그런 지시가 있을 때만** 표시합니다. 요약에서 찾지 못했다는 이유로 문서 전체에 정보가 없다고 단정하지 않습니다. 예산 숫자를 찾았어도 VAT·상한·장비 내역·조건을 빠뜨리면 검토가 필요합니다. 상충하는 후보가 있어도 파일명 연도나 다수결로 하나를 확정하지 않습니다.

`quality.json`은 각 주장의 인용문과 답변의 표현 차이를 찾는 보조 진단입니다. 숫자 환산이나 표현 변경으로도 플래그가 생길 수 있고, 플래그가 없어도 인용이 주장과 무관할 수 있습니다. 최종 의미 검토는 사람이 원문을 확인해야 합니다.

## 6. 실행 기록과 사람 검토

실제로 실행한 작업마다 `phase5_outputs/runs/` 아래에 별도 실행 폴더를 만듭니다. 노트북 출력에서 정확한 경로를 확인하세요.

| 파일 | 내용 |
| --- | --- |
| `result.json` | 생성 상태·출처·항목별 요약·원문 처리율 |
| `answer.md` | 검증된 답변·요약을 읽기 위한 Markdown |
| `quality.json` | 숫자·단위·VAT·기간·조건 보존 진단 |
| `human_review.json` | 이 결과와 원문에 연결된 사람 검토 양식 |
| `run.json` | 실행 정보·사용량·비용 추정 기록 |

검토 양식의 `reviewer`에 이름(예: `유영관`)을 적고, `rows` 안의 `supported`, `complete`, `conditions_preserved` 값을 원문을 확인한 뒤 `true` 또는 `false`로 작성합니다. 미검토 값은 `null`로 둡니다. `notes`에 검토 내용을 적을 수 있습니다. fingerprint·문서 ID·항목 ID·주장과 인용은 수정하지 않습니다. 검토 양식을 자동 승인하거나 다른 답변의 양식으로 바꾸지 않습니다.

검토 결과를 확인하려면 마지막 코드 셀의 `REVIEW_PATH`에 수정한 `human_review.json` 경로를 지정하고 그 셀만 실행합니다. 결과가 바뀌면 기존 양식을 그대로 재사용할 수 없습니다. 검토가 끝나지 않았으면 `review_pending` 상태가 정상입니다.

## 7. Phase 5를 판단할 때

다음 세 가지를 분리해서 봅니다.

1. **코드·원문 연결:** 기본 Run All과 로컬 테스트가 통과했는가.
2. **실제 생성:** 선택 문서 전체 요약이 실제 API 또는 해당 요청의 캐시로 실행됐는가.
3. **내용 검토:** 11개 항목이 원문을 뒷받침하며 금액·VAT·기간·기산점·예외 조건을 보존했는가.

제공 패키지의 오프라인 검증은 1번을 확인합니다. 사용자의 로컬 실제 요약 출력과 사람 검토를 확인하기 전까지 2·3번을 완료로 표시하지 않습니다. 개발에 이미 사용한 dev·기존 holdout 결과를 새 독립 평가처럼 보고하지 않습니다.

## 문제 해결

- **SDK 미설치:** 노트북 첫 셀의 Python 경로로 `-m pip install -r requirements-phase5.txt`를 실행하고 커널을 Restart합니다.
- **인덱스 버전 불일치:** 기존에 성공한 Phase 3 커널을 선택하거나 저장 버전으로 설치합니다. 인덱스를 지우거나 자동 재구축하지 않습니다.
- **429/크레딧·요청 한도:** API 계정의 잔액과 한도를 확인합니다. 같은 셀을 반복 실행하는 것으로 잔액 부족이 해결되지는 않습니다.
- **출처 검증 실패:** 해당 실행의 `result.json`과 진단을 확인합니다. 검증 실패한 생성 문장을 정답으로 사용하지 않습니다.
- **요약 상한 초과:** 실행 전 계획의 `block_reasons`를 확인하고 필요한 상한을 검토합니다. 기본적으로 자동 상향하지 않습니다.

기존 Phase 4의 자세한 배경은 동봉된 `README_PHASE4.md`에서 볼 수 있습니다. 이번 실행은 `README_PHASE5.md`와 08번 노트북을 기준으로 진행하세요.
