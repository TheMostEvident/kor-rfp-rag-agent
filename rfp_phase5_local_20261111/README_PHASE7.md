# Phase 7 — 품질·속도·사용량 평가

Phase 6의 실제 대화·검색 경로를 평가합니다. 기존 가상환경, 원문과 인덱스를 사용하며 재설치·재색인하지 않습니다.

## 실행

업데이트 후 기존 Python 커널을 Restart하고 `notebooks/14_younggwan_phase7_evaluation.ipynb`를 Run All 합니다.
기본 실행은 API 0회입니다. 개발용 60문항에서 같은 대화 라우터와 문서 선택을 사용해 두 검색 프로필을 비교합니다.

| 프로필 | 검색 방식 |
| --- | --- |
| literal_bm25 | 현재 원래 사용자 질문을 BM25로 검색하는 비교 실험 |
| phase6_rrf | 실제 Phase 6 맥락 해소·본문 질문 확장·후보 우선순위·문서별 문맥 할당 |

이는 같은 조건에서 만든 비교 실험이며 과거 Phase 3 성적과 같은 실험이 아닙니다.
질문·사용자가 선택한 문서 맥락만 실행 경로에 전달합니다. `target_doc_ids`, 필수 사실·정답값·기대 상태는 검색 후 채점용입니다.
후속 질문은 원래 사용자 턴만 순서대로 실행하고 사례가 바뀌면 대화 상태를 초기화합니다.

CLI도 기본값은 API 0회입니다.

```bash
python rfp_phase5_local_20261111/scripts/phase7_evaluate.py
python rfp_phase5_local_20261111/scripts/phase7_evaluate.py --case-id F001 --case-id D001
```

## 측정값

| 값 | 의미 |
| --- | --- |
| source span recall | 실제 입력 청크의 합집합이 필수 원문 인용의 공백 외 문자 전체를 덮은 비율 |
| first source overlap MRR | 처음 관련 원문과 겹치는 결과의 역순위. 전체 인용 확보와 구별 |
| scope/status match | 문서 범위와 상태 라벨의 일치. 의미적 정답률과 구별 |
| citation source validity | 독립 원문 레지스트리로 인용을 재검사한 비율. 주장 전체가 인용에서 도출되는지는 별도 검토 |
| p50/p95 | 현재 하드웨어·열린 인덱스에서의 한 차례 측정. 새로운 실제 API 요청과 로컬 캐시를 분리 |
| API/tokens/cache/failures | 동일 생성 클라이언트의 전후 사용량 차이. 실패·중단 요청의 사용량 미확인은 별도 기록 |

`at_k`는 실제 입력 청크 순서의 상위 3·5·8개입니다. 전체 입력 확보율도 따로 기록합니다.
비교 질문은 문서별 할당량 때문에 전체 입력이 8개보다 많을 수 있습니다.
라벨이 정렬되지 않은 경우 확보율을 100%나 0%로 가정하지 않고 `null`과 미정렬 수를 남깁니다.
인용이 없는 답변에는 인용 유효성 100%를 부여하지 않습니다.
시간 측정은 준비된 대화의 `ask()` 범위이며 인덱스 로딩·사례 준비 시간은 제외합니다.
사례별 대화 격리에는 제목·ID 등의 메타데이터만 복사하며, 전체 원문 레지스트리와 인덱스는 공유합니다.

## 전체 요약

Phase 5의 `content_documents/`가 들어 있는 실행 폴더를 노트북 `SUMMARY_RUN` 또는 CLI `--summary-run`에 지정합니다.
선택한 dev 요약 사례에 대응하는 저장 결과가 있으면 latest 지문·원문 SHA·문서 전체 청크·인용을 재검사합니다.
11개 항목 상태와 검증 결과를 남기고, 정답 사실은 사람 검토용으로 연결합니다.
원래 요약·검토표를 덮어쓰거나 모델을 재실행하지 않습니다. 이전 생성 사용량을 이번 API 비용에 더하지 않습니다.
없는 요약은 `no_saved_content_revision`으로 기록합니다. 상위 청크 요약으로 대체하지 않습니다.
저장 요약이 없는 평가 사례도 원문 등록·검색 대상에는 그대로 포함됩니다.

```bash
python rfp_phase5_local_20261111/scripts/phase7_evaluate.py \
  --summary-run 기존_Phase5_실행폴더
```

## 검색·문서 범위 개선 후 재확인

예산 본문과 공란 가격제안서의 순위를 구분하고, 사업명·기관명은 문서 선택에 사용합니다.
동명 사업은 선택 범위·기관·연도를 함께 대조하며, 사업명에 들어 있는 `전자`를 지칭어로 처리하지 않습니다.
사업명으로 확인 질문에 답하거나 약칭으로 문서를 전환해도 요청 항목을 이어 처리합니다.
두 문서를 차례로 조회한 뒤 비교할 때는 최근 문서 ID를 사용하고 각 문서에서 근거를 다시 검색합니다.
전환할 문서가 아직 확인되지 않았다면 다음 후속 질문도 확인을 이어가며 이전 문서에서 답하지 않습니다.

숫자가 채워진 예시·서식도 원문 위치의 문맥을 확인해 실제 사업예산보다 우선하지 않도록 합니다.
문맥 검사는 예산 라벨과 금액의 정확한 원문 범위에 적용합니다. PDF의 페이지 머리말이 이전 서식의
문맥을 물려받더라도 새 사업개요에 있는 예산을 서식으로 취급하지 않습니다. 서식 자체를 묻는 질문은 유지합니다.
이 순위 규칙은 인용의 의미적 정답을 판정하거나 원문을 수정하지 않습니다.

업데이트 후 기존 **14번 노트북을 커널 Restart → Run All** 하면 개선된 검색·문서 범위를 재평가합니다.
인덱스 재구축이나 Phase 5 요약 재생성은 필요하지 않습니다. 실행 기록은 새 폴더에 저장됩니다.
그다음 `RUN_LIVE_EVAL=True`로 같은 기본 6턴을 실행해 생성 답변의 숫자·인용·조건을 원문과 대조합니다.
오프라인 검색 근거 확보율은 생성 답변 정확도가 아닙니다.

동일한 개발용 60문항의 개선 전후 결과는 다음과 같습니다. 정답과 기대 문서 ID는 검색 이후 채점에만 사용합니다.

| 항목 | 개선 전 | 개선 후 |
| --- | ---: | ---: |
| Phase 6 경로의 필수 원문 근거 확보 | 102/141 (72.3%) | 130/141 (92.2%) |
| 문서 범위 일치 | 63/71턴 | 71/71턴 |

같은 새 문서 선택기를 쓰는 BM25 비교 실험은 105/141 (74.5%)입니다.
개선 전 60.3%와 비교할 때는 문서 선택기 변경도 포함된다는 점을 구별해야 합니다.
개발 세트에서 기존보다 원문 확보율이 낮아진 행은 없으며, 별도의 미열람 표본 성적이나 실제 생성 정답률을 뜻하지 않습니다.

## 소수 사례의 실제 답변

비교 질문은 문서별로 입력 근거를 분리해 생성하고, 각 문서 범위에서 인용을 검증한 다음 표로 합칩니다.
한 문서라도 검증을 통과하지 못하면 생성 결과를 표시하지 않으며 자동 재시도하지 않습니다.
전체 비교 요청의 크기·호출 상한은 첫 호출 전에 함께 검사합니다. 모든 요청은 같은 생성 클라이언트의 사용량에 누적됩니다.
기본 6턴에서도 비교는 문서 수만큼 호출을 사용할 수 있고, 요청 결과의 근거가 없으면 모델 호출을 생략할 수 있습니다.

최종 낙찰업체·실제 계약금액만 요청했는데 검색 입력에 해당 결과를 뒷받침할 명시적인 값이 없으면,
과업예산·평가방식을 대신 답하지 않고 `insufficient_evidence`와 추가 확인할 낙찰 결과 공고·체결 계약서를 안내합니다.
이는 현재 입력의 근거 부족이며 문서 전체나 실제 낙찰 결과의 부재를 단정하지 않습니다.
예산과 실제 계약금액을 함께 묻는 질문이나 결과 값 후보가 있는 질문은 일반 생성·엄격한 출처 검증으로 이어집니다.

노트북의 `RUN_LIVE_EVAL=True`를 명시하면 기본 사례에서 최대 6턴을 실행합니다.
문서 허용 목록은 선택 사례의 **사용자 선택 문서 맥락**에서 구성해 먼저 보여 줍니다. 정답 대상 ID를 사용하지 않습니다.
기존 `.env`에서 키를 읽으며 값은 출력·저장하지 않습니다. 전체 평가가 하나의 생성 클라이언트와 호출 상한 8회·입력 바이트 상한을 공유합니다.
사례별로 상한을 초기화하지 않으며, 서비스·예산 오류 후 자동 재시도하지 않습니다.
프로세스나 클라이언트를 새로 만들면 실행 상한도 새로 시작합니다. 달러 결제 한도가 아닙니다.

CLI에서는 사례와 API 전송 허용 문서를 모두 지정합니다.

```bash
python rfp_phase5_local_20261111/scripts/phase7_evaluate.py \
  --live --case-id F001 --approve-doc-id 선택한공개문서ID
```

`pricing` 기본값은 `null`입니다. 금액을 모르는 것을 0달러로 표시하지 않고 실제 토큰 수를 기록합니다.
공식 단가를 확인한 경우 모델명과 input/cached-input/output의 백만 토큰당 단가를 설정하면 USD 추정치를 계산합니다.
설정 단가의 최신성은 자동 보증하지 않습니다. 추정치는 보고된 토큰 기준이고 세금·미확인 실패 사용량 등을 포함한 청구서가 아닙니다.

## 결과와 사람 검토

모든 기록은 Git에서 제외한 `phase7_outputs/runs/<실행ID>/`에 저장합니다.

`validation_failed_turns`와 `generation_error_turns`는 답변 차단 횟수를 별도로 표시합니다.
인용 유효성은 수용된 인용만의 비율이므로 검증 실패 0회를 뜻하지 않습니다.
비교 한 턴에 새 호출과 캐시가 함께 있으면 `mixed_live_cache_latency`로 분리합니다.
실패 시 노트북에 검증 사유·문서별 검사 결과를 표시하며, 검증되지 않은 모델 인용문을 답변으로 표시하지 않습니다.
실제 답변 셀을 재실행했다면 아래의 검토 집계 셀과 마지막 검증 셀도 다시 실행해 최신 실행을 표시하세요. 추가 API 호출은 없습니다.

- `report.json`: 실행 코드·설정·문항·인덱스의 지문, 개별 결과, 실제 입력 근거, 누락, 속도와 사용량
- `human_review.json`: 이 결과에 연결된 빈 사람 검토 양식. 검토자가 `null`을 `true/false`로 바꿉니다.

정확성·인용의 주장 지지·조건 보존·필수 사실 누락·유보/확인 질문 적절성을 원문과 대조합니다.
검토자 이름을 기록하고 노트북의 검토 집계 셀 또는 다음 명령을 실행합니다. 추가 API 호출은 없습니다.

```bash
python rfp_phase5_local_20261111/scripts/phase7_evaluate.py --review-run 해당_Phase7_실행폴더
```

검토하지 않은 행은 정확도에서 정답으로 간주하지 않습니다. 검토한 행의 정확도와 전체 표본 검토율을 같이 보고합니다.
실제 실행이 모두 완료되고 전체 선택 표본의 검토가 끝난 경우에만 그 표본의 정확도를 계산합니다.
대역 응답·일부 검토·일부 실행의 성적을 실제 전체 표본 정확도로 승격하지 않습니다.

## 범위와 완료 판단

이 단계는 개발용 데이터에 대한 측정입니다. 과거 열람 이력이 있는 기존 holdout은 새 독립 평가로 재사용하지 않고 질문 파일을 열지 않습니다.
합성 파싱 장애 도구 결과를 이 검색 경로에서 실제 장애로 가장하지 않습니다. 해당 사례는 명시적으로 제외하고 수를 보고합니다.
문서 선택기의 후보 목록은 활성 문서로 주입하지 않으며, 해당 조건은 사례별 주석에 남깁니다.

검색·출처·문서 범위의 실패 사례를 확인하고, 실제 대표 사례의 내용 검토와 속도·비용 측정이 끝나면 개발 표본에 대한 Phase 7 평가를 마무리할 수 있습니다.
측정 도구 테스트가 통과한 상태와 실제 서비스 품질을 확인한 상태는 결과에서 구분합니다.
Phase 8의 운영·파일럿에 앞서 새 문서·새 질문으로 독립 표본을 구성해 적용 범위를 확인합니다.

```bash
cd rfp_phase5_local_20261111
python -m unittest rfp_phase7.test_evaluation rfp_phase6.test_session rfp_phase6.test_retrieval -q
```
